# `zynqberrydemo`

Getting anything to run at all on the ZynqBerry. Derived from Trenz's "Demo 1".

## Installing Vivado and Petalinux

Download 2024.2 from AMD and install them in `/opt/Xilinx` and `/opt/petalinux` respectively.  The Vivado installer is quite opaque; choose Vitis with all the trimmings, and then narrow the board support to just Zynq7000.

## Building block design

The project already has a suitable block design built; you can open it using the Trenz-supplied `vivado_open_existing_project_guimode.sh`.  In Vivado, choose "Generate Bitstream", and let it work.  When it finishes, there's no need to open anything.  Instead, choose File > Export > Export Hardware, select the radio button which includes the bitstream, and emit to `zynqberrydemo/xsa`.

### Block design info

The key components of the block design are are:

+ PS7 embodying control points + settings for interfacing with the PL.
+ The custom RTL, `axis_add1`.
+ AXI DMA engine connected to the custom RTL.
+ Two AXI interconnects which join the DMA engine to the PS:
  + S_AXI_LITE to M_AXI_GP0.
  + M_AXI_MM2S and M_AXI_S2MM both to S_AXI_HP0.
+ Concat joining the two interrupt lines from the DMA engine to the PS.
+ Reset block.

The clocks are all driven by FCLK0. AXI data widths should be 32 bit. Be careful about `AXI` vs `AXIS`.

## Building Petalinux

```sh
cd os/petalinux
petalinux-config --get-hw-description=/home/ubuntu/xilinx/zynqberrydemo/xsa
# we've already included some config details, like enabling the DMA engine kernel module
petalinux-build
```

Lastly, we will want to build the demo components.

```sh
petalinux-build --sdk  # this will take a long time, it's generating a whole cross-compiler toolchain
bash images/linux/sdk.sh -d sdk
source sdk/environment-setup-*

# KDIR is baked into the Makefile, but you can find yours by running
# find build/tmp/work -type d -name '*standard-build' | grep linux-xlnx

cd ../axisdma_demo
${CC} -O2 -Wall -o axisdma_test axisdma_test.c
make  # builds kernel module, axisdma_shim.ko
```

Also, you'll need to convert `os/petalinux/images/linux/pl.dts` to a `.dtbo`.  You can probably run the following command in any Linux environment, though I did this on the ZB itself:

```sh
dtc -@ -I dts -O dtb -o axisdma-test.dtbo axisdma-test.dts
```

You also need to wrap the FPGA bitstream into a `.bin` for future use with `fpgautil`:

```sh
bootgen -image system_bit.bif -arch zynq -process_bitstream bin -w -o system.bit.bin
```

## Running demo

The SD card needs the following files:

```
# Linux kernel + rootfs generated by Petalinux, found in os/petalinux/images/linux/
image.ub    # kernel + whole initrd filesystem
system.dtb  # maybe, might be included in image.ub
boot.scr    # maybe, might be included in image.ub

# bitstream + device overlay
zsys_wrapper.bit.bin  # comes from os/petalinux/images/linux/system.bit.bin
pl.dtbo               # or pl.dts, if you want to convert it on the board

# PS binaries to drive PL
axisdma_shim.ko    # kernel module
axisdma-test.dtbo  # device-tree overlay for the AXI shim
axisdma_test       # actual userland test
```

Attach picocom and let the ZB fully boot.  Then, run the following:

```sh
# QSPI image sets DMA channels to 64b wide, but our demo is 32b wide
devmem 0xF8008000 8 0x01
devmem 0xF8008014 8 0x01

mkdir /mnt/sd
mount /dev/mmcblk0p1 /mnt/sd
cd /mnt/sd

fpgautil -b zsys_wrapper.bit.bin -o pl.dtbo

mkdir -p /sys/kernel/config/device-tree/overlays/axisdma_test
cat axisdma-test.dtbo > /sys/kernel/config/device-tree/overlays/axisdma_test/dtbo

insmod axisdma_shim.ko

./axisdma_test
```

## Appendix: Imaging QSPI for the first time

Here are my slightly-less-than-raw notes about getting the board to boot for the first time, which primarily requires imaging QSPI. For posterity, I've included a `qspi/` subfolder with the major artifacts.

+ First goal was to run the [basic Trenz demo](https://wiki.trenz-electronic.de/display/PD/TE0726+Zynqberry+Demo1) as-is, or nearly as-is.
+ Vivado / Vitis can't run natively on an aarch64 MacBook. EC2 m7i.2xlarge + 300 GiB drive + Ubuntu will do.
    + The demo uses the 2024.2 version, and you really do need to follow that.
    + The mapping between software components needed by the demo and the installer GUI is not super clear. I think I had best luck choosing "Vitis", enabling most of the pure software components, then down-selecting to just the board I intended to use: Zynq7000 and, for good measure, Virtex (which the board self-advertises as in some contexts). Also, Petalinux is a separate install; be sure to grab that too.
    + Xilinx doesn't insert itself into your path; you have to `source /opt/Xilinx/Vivado/2024.2/settings64.sh` and similar for `Vitis`, `Vitis_HLS`, and `petalinux`.
        + There are also some useful tools at `Vitis/2024.2/gnu/aarch32/lin/gcc-arm-none-eabi/bin/arm-none-eabi-*`, which never end up on the path.
+ LBNL's [XVC-FDTI-JTAG](https://github.com/BerkeleyLab/XVC-FTDI-JTAG) is a portable Xilinx Virtual Cable, a JTAG-over-TCP protocol, which advertise the ZynqBerry to the EC2 instance.
    + It "runs fine" on macOS, but isn't actually usable: ZB exposes two serial channels, one for JTAG and one for a UART console, both of which will be simultaneously needed down the line; however, when `fdtiJTAG` launches, it asks macOS for control of the JTAG channel, and macOS cheerfully destroys *both* serial channels, so that `/dev/tty.usbserial*` is no longer populated.
    + I switched to an old (2014, B+) Raspberry Pi. (In turn, this necessitated a run to get a powered USB hub: the Pi gets its power over USB, as does the ZynqBerry, and daisy-chaining them made the Pi loudly concerned about voltage drops.)
+ ZynqBerry can only boot off of JTAG (i.e., live instruction) or QSPI (i.e., onboard flash), but the QSPI starts empty and there's no way to write to it directly from a remote. First real goal then was to write a flexible bootloader to QSPI.
    + The prebuilt version of the Trenz demo doesn't explicitly cover ZE0726-04, so I decided to build from source.
    + The first demo build instructions require knowing the long-form part number of the board; only the short-form TE0726-04 is printed on mine's surface, but the long form TE0726-04-41C98-A was in my email.
    + Before executing any of the scripts inside of the demo source, it would have been expedient to make some opaque modifications. If you `rg` through the tree for `FSBL: Enabling VTC..`, you'll find some hits inside of `TE_FsblHookBeforeHandoff`, potentially in a few different files. Remove all that logic, or anyway make it non-fatal.
    + From here, the image assembly instructions basically work.
    + What _doesn't_ work is the JTAG boot script. The manual steps are:
        + Connect ZB to the Pi (with S1 in JTAG mode, toward the USB ports), start `./ftdiJTAG` on the Pi, and `ssh -R 2542:localhost:2542 ubuntu@ec2-ip-address` (and, for me, `-i ~/.ssh/….pem`). Finally, open `picocom -b 115200 /dev/ttyUSB1` to eventually get ready to interrupt u-boot. Right now LEDs should be solid green + solid red.
        + On EC2, start `hw_server` (in Vivado Tcl console), then launch `xsct` in a terminal for interactive use and drive the steps in `flash_over_jtag.tcl`.
        + Make sure the first partition of the SD card is FAT32. Write `BOOT.BIN` to it, unmount, and insert into the SD card slot on the underside of the board.
            + I wrote a custom `BOOT.BIN` which contains exactly `zynq_fsbl.elf` and `u-boot-dtb.elf`. The default one has `u-boot.elf` and `system.dtb` instead. I thought `u-boot.elf` was causing problems, but it was actually that I skipped the `VTC` stuff above, so I think it might work fine if I were to try it again.
        + In the Picocom console connected to ZB, run the commented-out steps at the bottom of `flash_over_jtag.tcl`.
