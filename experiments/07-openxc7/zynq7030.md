# XC7Z030-SBG485 compile check

`run_zynq7030.sh` builds a counter and a BRAM/DSP workload for `xc7z030sbg485-1` on Apple Silicon, through placement, routing and bitstream assembly. **These are compile-only images.** The XDC selects package-valid pins, not board-safe connections.

## Run

Install the [pinned native packages](README.md#setup), Python 3.11 or newer, and Icarus Verilog, then run:

```sh
./run_zynq7030.sh
```

The first run downloads AMD's 167 KiB pinout archive and generates the chip database. Later runs reuse both. `ERL_HLS_ZYNQ_PINOUTS` selects an already-downloaded archive; `ERL_HLS_APIO_HOME` and `ERL_HLS_OPENXC7_BUILD_ROOT` select the tools and output directory. The script verifies the archive, input database files and installed tool releases before building.

## Package mapping

The pinned Project X-Ray database contains the XC7Z030 fabric and FBG676 bonding, but no SBG485 package directory. The overlay joins pins by **bank and pin-function name**, using [AMD's package files](https://www.amd.com/en/developer/resources/adaptive-socs-and-fpgas/package-pinout-files/zynq-7000-package-device-pinout-files.html). It first checks all 402 FBG676 database entries against AMD, then resolves 302 SBG485 entries, including all 150 programmable I/O pins in banks 13, 34 and 35. Every assigned site must exist in the fabric grid. Ambiguities, unknown functions and missing programmable pins fail the build.

The two packages use the same XC7Z030 silicon. Its configuration-frame layout, bank locations and IDCODE (`0x0372c093`) are reused unchanged; package pins are remapped. A content-addressed overlay links to the installed database, leaving it untouched. Its manifest records input/output hashes, and its identity participates in the chip-database cache key. Keep the installed database available while using the overlay.

## Validation

The fast regression checks rejected mappings and compares 4,096 resource-workload output cycles with a Python reference, covering eight RAM sweeps. CI runs this regression without downloading FPGA tools or vendor pinouts. The native build additionally requires exactly one BRAM and one DSP after synthesis, then decodes each assembled bitstream and checks every non-ECC configuration bit against the input frames. This catches serialization loss; it does not establish silicon behavior. The bundled BRAM simulation primitive has no behavioral model, so the RTL simulation precedes technology mapping.

The [recorded native run](zynq7030-result.json) used the pinned August 2026 packages on 2026-09-20:

| Workload | Placed LUT BELs | Placed FFs | RAMB18E1 | DSP48E1 | Decoded set bits |
| --- | ---: | ---: | ---: | ---: | ---: |
| Counter | 49 | 24 | 0 | 0 | 1,176 |
| BRAM/DSP | 67 | 73 | 1 | 1 | 4,731 |

Both completed bitstream assembly. This is one placement per workload, not a seed-distribution or performance benchmark. Reports retain the requested 100 MHz constraint, but **do not qualify that clock**: [nextpnr's missing BRAM/registered-DSP timing arcs and shared speed tables](phi-timing.md#measurement-limits) apply here too.

Outputs under `build/zynq7030-{counter,resources}/` include mapped RTL, netlists, Yosys/nextpnr logs, utilization/timing reports, FASM, frames, bitstreams and decoded bits. The manifest lives beneath `build/databases/`; deterministic frame hashes identify the configuration independently of timestamp-bearing bitstream headers.

## Remaining qualification

Before programming hardware, verify schematic pins and bank voltages, clock/reset sources, and configuration/boot settings. The [PS7/FCLK0/GP0 register probe](../../docs/zynq-ps-probe.md) separately checks PS-interface compilation and register behavior; board DDR/MIO initialization, transceivers and physical I/O remain separate tests. Presence of their package pins in the overlay does not establish support for those blocks. Hardware operation and complete timing closure remain unverified.
