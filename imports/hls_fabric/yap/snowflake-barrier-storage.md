# Snowflake barrier and storage comparisons

Compare complete ordinary-actor D3/H3 decoders with the retained 128-sheet, 0.5% noise cohort. Preserve vertex transitions, correction ownership/order, phase ordering, mailbox capacities, eight outstanding source requests, two-stage XLS schedule and failure handling. The direct/flat baseline is commit `5c4d222`: 887.54 clocks mean round spacing; native XC7/ZU7 area exceeds both devices. No implementation has a qualified clock.

Registered hypotheses before measurement:

- A six-by-six completion tree reduces the coordinator's per-phase input population from 36 to six. A first ordinary-actor tree still serializes each local group; at four clocks per acceptance its fully ready intake component has roughly two six-input stages rather than one 36-input stage. This is a component estimate (about 48 versus 144 clocks), not a round-time prediction: readiness overlaps, actor entries, routing and the latest vertex still matter. Added collector actors may increase area. A generic buffered-join lowering is a distinct follow-on if actor overhead dominates; no decoder-specific RTL replaces the Erlang protocol.
- Six and twelve vertex executors move actor data and payload mailboxes to BRAM and share callback logic. Expect substantially less replicated service logic, with additional RAM/control cost and longer admission-to-publication spans. Do not predict an area ratio from isolated mailbox cone percentages. Root coordinator remains direct to isolate storage from barrier intake.
- Combining the tree with shared execution can expose vertex service that the flat coordinator previously hid. The result can be slower than the tree alone even when it is better than the original design. Compare actual whole-round spacing and the separately observed phase spans.

Measure direct/flat, direct/tree6, six-executor/flat, twelve-executor/flat, then the corresponding shared/tree6 variants if their correctness gates pass. A source-held backlog is not hardware occupancy. Report minimum, mean, population variance and maximum; distinguish handshakes from callback execution and resource order from causality.

After the direct/tree and six-executor/flat burst probes, before observing either shared/tree result: direct/tree leaves mean command-to-last-vertex-publication unchanged (50.13→49.98 clocks), while six-executor/flat stretches it to 169.18. The six-executor flat root now needs only 23.45 clocks after the latest vertex publication. Predict that adding the tree to six shared executors changes step cycles by roughly ±10%, possibly worsening them, rather than reproducing the direct tree's 2.2× speedup: the remaining serial vertex/scheduler/neighbor path already spreads publications, and a second barrier can add latency after the latest producer. Twelve executors may improve that upstream span more directly. These are clock-count forecasts, not physical frequency or area claims.

The source audit after the first native runs found that declaring `sf_barrier_config` extends tag/length validation in all generated services, even those which reject that message. The old baseline therefore measures the total pre-change delta, not collector topology alone. Add a current-protocol flat/dedicated control before claiming a tree-only delta. No measured workload sends this configuration to vertices or the root; expect unchanged algorithm decisions, roughly unchanged cycle counts and less than 1% service/area difference from the old baseline. This estimate follows the generated-source diff and the already observed small vertex-service area increase in the tree run; it is not an independent prior for the original experiment.

The shared/tree burst result rejects the ±10% forecast: six-executor mean spacing falls 1,415.86→770.14 clocks, and command-to-last-vertex-publication falls 169.18→90.05 while mailbox admission remains 7. Before adding pressure observations, test whether downstream completion congestion feeds back through the shared router: expect flat completion lanes and/or scheduled-batch input to accumulate at least twice the blocked port-cycles of the tree. Observe valid offers separately from accepted publication, plus batch-input, credit and lookahead-window handshakes. A late accepted publication alone does not establish late production; an output-held batch can also delay subsequent actors. If held offers do not account for the change, inspect the changed routing/window arbitration instead. Port-cycle sums can overlap and will not be subtracted directly from whole-round latency.

The added pressure recording supports that feedback mechanism. Over the same 2,016 completions/5,088 accepted effect batches, flat6→tree6 completion-offer wait falls 16.740→0.337 clocks on average (maximum 27→3). Scheduled-batch input blockage falls 33,906→833 **port-cycles**; 33,733 of the flat case's blocked input samples coincide with a blocked completion offer on that same router (99.49%). The generated router joins downstream publication before advancing and returning credit. Last first-valid offer also moves 145.18→89.63 clocks after command, so congestion delays later batches as well as holding the currently offered completion. The ±10% forecast mistook the late accepted-publication endpoint for an invariant upstream cost. These overlapping port samples explain feedback, but do not independently allocate whole-round critical-path time or measure callback execution.
