# XLS-facing generation

These Erlang modules lower checked plans into DSLX and compose source artifacts for XLS. They also retain the physical interfaces needed by their surrounding hardware. This directory is broader than text emission: the public composition facades prepare source and choose a supported lowering path, while smaller renderers consume already checked facts. [Planning](../../planning/README.md) owns reusable topology, schema and layout authorities; it may itself retain XLS-specific representations.

The two execution paths meet the compiler at different boundaries:

- `hls_source_build` calls `hls_protocol_transport` to prepare source-protocol programs and receiver ownership. `hls_local_actor` composes ordinary compiler functions with `xls_activation_codegen` and `xls_local_owner`. `xls_protocol_inbox` installs the checked inbox layout. `hls_protocol_network`, `boundary`, `bridge`, `application`, `deployment` and `mixed` compose progressively larger bundles through their matching `xls_protocol_*` renderers. They retain the same transport plan rather than recompiling actors at each layer.
- `hls_scheduler_build` prepares `xls_fabric_topology_dslx`, then compiles the required actors with `xls_scheduler_actor`. `xls_scheduler_codegen` adds scheduler RAM loading, selection and publication around `xls_machine_codegen`. Topology emission selects retained compact scheduler or materialized-instance graphs; `xls_topology_scheduler_dslx` and `xls_fabric_topology_instance_dslx` render those choices.

`xls_machine_codegen` is shared physical execution support, not a third scheduler. Collection, gather, event, reduction and publication modules contribute checked fragments to its owners. `xls_collection_observation` and `xls_scheduler_observation` keep the associated DSLX and wrapper interfaces together; their small SystemVerilog connection fragments use the same observation authority rather than a parallel schema.

For the legacy partition path, `hls_partition_dslx` and the `links`, `outbox`, `shared_dslx`, `reduction_dslx` and `tile` helpers emit placed physical wrappers. `hls_partition_tile` combines specialization with parameter rendering; it is deliberately target-facing. `xls_partition_application` composes a gateway shell around the resulting partition graph. These entrypoints remain distinct from the public source/scheduler build frontends.

To extend a generated block, first find the retained input plan and its owner. Put reusable behavioral code in `priv/xls/`; use `xls_template` only for explicit checked template slots and Erlang renderers for static dimensions, names and connections. Preserve `xls_emitted` artifacts while composing compiler output so their failure codebooks stay attached. Extract bytes only for an output file or another documented byte boundary. Runtime record packing, transport sessions, external tool invocation and application examples do not belong here.
